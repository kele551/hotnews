# REVIEWING —— 收到改动之后怎么验、怎么发（维护者用）

> 这份是**维护者侧**的流程：别人（人或 AI 助手）提了改动，你怎么复核、哪些必须自己做、什么时候发版。
> 面向改动者的最短路径见 [CONTRIBUTING.md](CONTRIBUTING.md)；可认领任务见 [../TASKS.md](../TASKS.md)。
> ⚠ 动升级链路前先读 [CONTRIBUTING.md](CONTRIBUTING.md) 第 5.2 节的两条红线。

## 一、回话（唯一无法自动化的一步）

- **目标：24~48 小时内给第一句回复**。哪怕是"收到，我这周看" —— 冷掉的 Issue / PR 是最劝退人的。
- 回复只讲三件事：**收到了什么 / 还需要什么 / 按什么标准验收**。
- 不想做或暂时不做，也要把**理由写下来**（这本身就是文档）。

## 二、复核（只认"验收输出"，不认"应该没问题"）

| 步骤 | 怎么做 |
|---|---|
| 1. 看范围 | 是否**一次一件事**？有没有夹带构建产物（`dist/`、`build/`、`runtime/`、`*.exe`）？`git diff --stat` 有没有"整个文件都变了"？ |
| 2. 跑闸门 | `python tools/preflight_release.py`（发版前**必须全绿**；含真机语料断言）；改抓取逻辑的还要看他贴的**实测三连**（能连通 / 带图 / 有当天内容） |
| 3. 看自证 | PR 里贴的命令与输出能不能对上改动？改了分流口径的，有没有**同时补断言**？ |
| 4. 查禁区 | 有没有碰 `AGENTS.md` 里的禁区（**本地 `version.json` 必须精简**、**不许强推 Gitee `master`**、替换脚本必须 UTF-16、红线词、本机路径/私人邮箱/令牌） |
| 5. 查文档 | 行为变了，README / `说明.txt` / `docs/` 有没有同步改？ |

> 复核时**不要**直接改别人的分支：把问题写成评论，让改动者自己改。

## 三、只有维护者能做的事（改动者做了也没用，提前说清）

- **改版本号**、**发版**、替换发行版附件、两平台同步；
- **动 `version.json` 的对外格式与签名**（在线升级的命根子）；
- **往 Gitee `master` 推改动**（必须用 CONTRIBUTING 5.2 的**做法二**，全程不碰 `version.json`；**永远不强推**）；
- **发布时机判断**（修复攒够一批、或距上次发版 1~2 周；用户能直接感知的缺陷优先发）。

⚠ 任何情况下都**不要把别人的 PR 直接 merge 到发布分支后就发版** —— 发版前必须自己跑一遍闸门。

## 四、合并之后（维护者收尾清单）

- [ ] 版本号按规则决定加不加（**不加号就别发版**，攒着）；
- [ ] 发版前：闸门全绿 → 打包 → 更新升级源（完整版 + 签名，两平台）→ 发行版 → 下载回来比对 SHA256；
- [ ] 推完 Gitee 后**回读确认** `git show gitee/master:version.json` 里 `launcher` 段还在；
- [ ] 在 `logs/` 记一句**升级链路自查**：线上版本号 > 上一版、用户检查更新可升级；
- [ ] 更新 `snapshots/` 与 `patches/`（维护者工作区侧）；
- [ ] 外部贡献：在 CHANGELOG / Release 说明里**写上感谢**。

## 五、别人改不动的那些地方，怎么处理

- **大改架构 / 改分流口径**：先让他在 Issue 里写方案 + 附实测数据，方案过了再动手；
- **没有 Windows 环境**：让他靠 CI 验证，或你本地代跑闸门并把输出贴回 PR；
- **AI 助手提的改动**：同样按上面的标准复核 —— 额外确认它**没有引入新的第三方依赖**、没有复制来路不明的代码
  （本仓库运行时只依赖 4 个宽松许可库：fastapi / uvicorn / feedparser / httpx；GPL 系一律不收）。
